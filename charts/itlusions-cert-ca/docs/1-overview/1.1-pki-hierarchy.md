# ITlusions PKI hierarchy

The ITlusions CA chart establishes a two-tier CA hierarchy using cert-manager. The root signs
purpose-specific intermediate CAs; applications request their certificates from an intermediate
issuer rather than directly from the root.

```text
itlusions-root-ca-bootstrap-issuer (self-signed)
  └── itlusions-root-ca (root Certificate; Secret: itlusions-root-ca)
      └── itlusions-root-ca-issuer
          ├── itlusions-workload-ca (intermediate Certificate)
          │   └── itlusions-workload-ca-issuer
          │       └── workload server and client certificates
          └── itlusions-database-client-ca (intermediate Certificate)
              └── itlusions-database-client-ca-issuer
                  └── database client certificates
```

The chart defines both intermediates in its [values](../../values.yaml).
Each Certificate has `isCA: true` and an ECDSA P-256 private key. The configured root duration
is `87600h` and each intermediate duration is `43800h`; these are certificate lifetimes, not
an implemented key-rotation policy.

## Resources and responsibilities

| Resource | Name | Purpose |
| --- | --- | --- |
| ClusterIssuer | `itlusions-root-ca-bootstrap-issuer` | Self-signs the root certificate. |
| Certificate | `itlusions-root-ca` | Root of trust; backed by `itlusions-root-ca`. |
| ClusterIssuer | `itlusions-root-ca-issuer` | Uses the root Secret to sign intermediate certificates. |
| Certificate | `itlusions-workload-ca` | Workload intermediate; backed by `itlusions-workload-ca`. |
| ClusterIssuer | `itlusions-workload-ca-issuer` | Issues workload certificates. |
| Certificate | `itlusions-database-client-ca` | Database-client intermediate; backed by `itlusions-database-client-ca`. |
| ClusterIssuer | `itlusions-database-client-ca-issuer` | Issues database-client certificates. |

The CA Certificates and Secrets are namespaced; the chart installs them in the Helm release
namespace. Deploy the chart in cert-manager's cluster-resource namespace, normally `cert-manager`,
because that is where the ClusterIssuers look for their CA Secrets. Leaf Certificates and their
Secrets belong in the application's namespace.

The bootstrap and root issuers are internal PKI plumbing. Consumers should use a purpose-specific
intermediate issuer. This is a convention, not an enforced restriction: the chart does not
prevent authorized users from requesting certificates directly from the root issuer.

## Purpose of the intermediates

- **Workload CA** (`itlusions-workload-ca-issuer`) issues certificates for application workloads.
  For example, an internal API can use a server certificate to authenticate its DNS name to
  clients; workloads can also use appropriately configured client certificates for mutual TLS.
- **Database Client CA** (`itlusions-database-client-ca-issuer`) issues client certificates for
  applications connecting to a database. The database must trust the issuing chain and apply its
  own policy to authenticate and authorize the certificate identity. The certificate used to
  authenticate the database server to its clients is a separate concern.

Both intermediates are signed by the same root. Their separation identifies the intended purpose
of issuance; it does not by itself restrict which certificates a verifier accepts. A verifier that
trusts the root can potentially accept a valid chain from either intermediate unless additional
trust, usage or identity policies restrict it.

The default [trust bundle](1.2-trust-distribution.md) contains only the public root, not the
intermediates. Normally, the TLS peer presents its leaf certificate and relevant intermediate,
allowing the verifier to build a chain to the trusted root. Check each integration: applications
may have different chain or trust requirements.

## Issue a workload certificate

For an API in the `default` namespace, a consumer can apply a Certificate like this:

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: example-api-tls
  namespace: default
spec:
  secretName: example-api-tls
  dnsNames:
    - example-api.default.svc
    - example-api.default.svc.cluster.local
  usages:
    - digital signature
    - key encipherment
    - server auth
  issuerRef:
    name: itlusions-workload-ca-issuer
    kind: ClusterIssuer
    group: cert-manager.io
```

cert-manager creates and renews the leaf certificate in the `example-api-tls` Secret in
`default`. The application or ingress must use that Secret and present the certificate chain.
Clients must separately trust the public root certificate and verify the service's DNS name.
This example does not create an application, Service, ingress, or trust distribution.

For database clients, use `itlusions-database-client-ca-issuer` and request the appropriate
`client auth` usage and identity for the database's authentication policy. The database must
also be configured to trust and authenticate those client certificates. The CA used by clients
to verify the database server may be different from the CA used by the server to verify clients.

## Add another intermediate

Add a uniquely named entry to the chart's `intermediates` list, including
its subject, duration, Secret name and ClusterIssuer name, then upgrade the chart. The
chart creates an intermediate Certificate signed by the root and a ClusterIssuer backed by that
intermediate. If supplying the list through an additional Helm values file, include all desired
entries: Helm replaces lists rather than merging their entries.

Separate intermediates organize certificate issuance by purpose, but they do not automatically
enforce isolation. A verifier that trusts the common root may accept chains from either
intermediate unless it applies additional trust or identity restrictions.

## Verify the hierarchy

After selecting the intended Kubernetes context and deploying the chart:

```powershell
kubectl config current-context
kubectl get certificate -n cert-manager
kubectl get clusterissuer
kubectl get jobs -n cert-manager
```

The three CA Certificates and the bootstrap, root, workload and database-client ClusterIssuers
should report `Ready=True`. The release's `ca-key-compat` post-install/upgrade job should have
completed. Verify a leaf Certificate separately in its own namespace:

```powershell
kubectl get certificate example-api-tls -n default
```

Readiness alone does not prove that an application presents the correct chain or that clients
trust and validate it; test a real TLS connection after configuring the consumer.

## Security and lifecycle

- The root is an online CA: its private key is stored in a Kubernetes Secret and is used by
  cert-manager. The intermediate Secrets also contain private keys. Restrict Secret access and
  who may request certificates; Kubernetes Secret read access exposes private keys.
- Distribute only the public root certificate as a trust anchor, never the CA Secret or its
  private keys. The optional [trust bundle](1.2-trust-distribution.md) distributes public
  certificates to selected Kubernetes namespaces. Trusting this private root is not the same as
  obtaining a publicly trusted certificate.
- The post-install/upgrade compatibility job reads and patches the CA Secrets, adding
  `ca.key` and setting `ca.crt` for CNPG compatibility. It is not a continuous reconciler; account
  for Secret changes and renewal when designing operations.
- Protect backups and plan CA renewal, rotation, trust overlap, leaf reissuance and revocation
  before relying on this PKI beyond a disposable cluster. The chart does not provide an automated
  rotation or revocation procedure. Recreating a disposable cluster without restoring the CA keys
  creates a new trust anchor and can invalidate existing trust.
- The local Keycloak and Argo CD ingress certificates in the ITlusions kind profile use separate
  CAs. Installing this chart does not migrate those services or configure their clients to trust
  the ITlusions root.
