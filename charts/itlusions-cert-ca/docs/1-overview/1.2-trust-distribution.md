# 1.2 Trust distribution

The optional trust-manager Bundle distributes the **public** ITlusions root certificate to
ConfigMaps. It does not distribute leaf certificates or private keys and does not configure
applications to trust the bundle automatically.

## Prerequisites and installation order

1. Install cert-manager and wait for its CRDs and webhook.
2. Install trust-manager as a separate release and wait for its controller and Bundle CRD.
   The ITlusions `itlusions-trust-manager` chart uses `cert-manager` as its trust namespace.
3. Install or upgrade this CA chart with `trustBundle.enabled=true`.

The `keycloak-oidc` kind profile does this in order. Outside that profile, ensure the
trust-manager trust namespace matches the namespace containing the CA Secrets before enabling
the Bundle. The CA and ClusterIssuer Secrets normally belong in `cert-manager`.

The default Bundle `itlusions-internal-trust` reads only the `tls.crt` **key** from the configured
root Secret and creates a `itlusions-internal-trust` ConfigMap with a `ca.crt` key in each target
namespace. Kubernetes Secret permissions are not key-specific: the trust-manager controller's
upstream Role can read, list and watch **all Secrets** in its trust namespace, including CA private
keys. Protect and restrict that controller and its namespace. Do not copy CA Secrets or private
keys to workloads.

## Select namespaces and consume the bundle

By default the enabled Bundle selects exactly `cert-manager`, `keycloak` and `operators` using
their Kubernetes-provided `kubernetes.io/metadata.name` label. Change `trustBundle.namespaces`
to select a different list, or set `trustBundle.namespaceSelector` to use labels instead.
Without a custom selector, an empty namespace list is rejected to avoid unintentionally
distributing to every namespace.

For label-based selection, supply chart values such as:

```yaml
trustBundle:
  enabled: true
  namespaceSelector:
    matchLabels:
      itlusions.io/trust-internal-pki: "true"
```

Only namespaces carrying that label receive the bundle. This overrides the default
`trustBundle.namespaces` list.

```powershell
kubectl get bundles.trust.cert-manager.io itlusions-internal-trust
kubectl get configmap itlusions-internal-trust -n operators
```

The Bundle condition should be `Synced=True`. Mount the ConfigMap in the consumer's namespace
and configure the application or its TLS library to trust `ca.crt`; check whether the application
reloads updated bundles or needs a rollout. The default bundle contains only the private root.
Set `trustBundle.includePublicCAs=true` if a consumer requires trust in both public CAs and the
private root, and maintain trust-manager's default CA package.

Trusting the root does not enforce isolation between intermediates: applications needing that
restriction must use an appropriate narrower trust or identity policy.

## Rotation and external clients

`trustBundle.additionalSources` accepts extra trust-manager sources, for example a second public
root during a controlled rotation. Add the new root and verify propagation before issuing leaf
certificates from it; remove the old root only after old leaves and clients have migrated.
Replacing the only source Secret without overlap can immediately remove trust in the old root.
Review the chart's CA key, certificate renewal and rollback procedures separately.

ConfigMaps do not install trust on host operating systems, browsers, kubelogin or the kind
control-plane API server. Those need an independent public-root distribution and bootstrap
mechanism. The Keycloak and Argo CD TLS certificates are also unchanged until separately
migrated to the workload issuer.

See the [trust-manager documentation](https://cert-manager.io/docs/trust/trust-manager/).
